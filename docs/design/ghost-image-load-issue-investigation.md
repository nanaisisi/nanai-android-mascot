# ゴースト・シェル画像未描画（壊れた画像アイコン表示）の修正検討書

## 1. 概要と現象

### 1.1 現象

- アプリ起動時やゴースト切り替え時、マスコット描画領域に**ブラウザ標準の壊れた画像アイコン**および「mock」や取り込んだゴーストの名称テキストのみが表示される。
- 期待される立ち絵（PNG/SVG等のサーフィス画像）が表示されない。

### 1.2 影響範囲

- デフォルトゴースト（`mock_nanai`）の初期描画
- ZIP等から取り込んだ外部ゴーストの描画
- シェル切り替え時の立ち絵更新

---

## 2. 原因分析

### 原因①: Tauri WebViewにおけるローカル画像アクセスの制限

- **詳細**: フロントエンド（`ghost.js` や `surface.js`）で `img.src =`${ghostPath}/shell/.../surface0.png`` のようにファイルシステムパスや相対パスを直接指定している。
- **問題**: Tauri（Windows環境ではWebView2）のセキュリティ機構により、`asset://` プロトコルや `convertFileSrc` 変換を介さないファイルシステム上のパスへの直接アクセスは、同一生成元ポリシー（SOP）またはセキュリティブロックにより遮断され、404 / ERR_FILE_NOT_FOUND になる。

### 原因②: シェル構造とファイル命名規則の差異

- **詳細**: 伺か仕様におけるシェル構造は一般に `[ゴースト]/shell/[シェル名]/surface0.png` であるが、以下の差異が存在する：
  - シェル名が `master` 以外の名称（取り込みゴーストによる）。
  - 大文字・小文字（`Surface0.png`, `SURFACE0.PNG`）。
  - 拡張子（`.png`, `.pna`, `.svg`, `.bmp`）。
- **問題**: パスの決め打ち（ハードコード）により、実ファイルが存在しても一致せず読み込みに失敗する。

### 原因③: エラー時のフォールバック処理・UI露出

- **詳細**: `<img>` の読み込み失敗（`onerror`）時に、`img` 要素自体が非表示化されず残存し、ブラウザ既定の「破損画像アイコン」がそのまま描画されている。

---

## 3. 改善・改修アプローチ

### アプローチA: フロントエンドでの画像URL解決とUIフォールバック（優先度：高）

1. **`convertFileSrc` によるURL正規化**:
   - TauriのAPI関数（`convertFileSrc`）を経由して、ローカルファイルパスをWebViewが解釈可能なURL（例: `https://asset.localhost/...`）に変換する。
2. **破損アイコンの非表示とプレースホルダー改善**:
   - `onerror` 発火時に `img.style.display = 'none'` を設定し、破損アイコンの露出を防止。
   - シルエットやデフォルトアイコン、洗練されたマスコット名バッジを表示する。

### アプローチB: Rustバックエンドによるサーフィス探索APIの整備（優先度：中）

1. **サーフィス探索コマンドの追加**:
   - バックエンドに `resolve_surface_image(ghost_name, shell_name, surface_id)` コマンドを設け、Rust側で実在する画像ファイル（拡張子や大文字小文字の差異を吸収）を探索・返却する。
2. **メリット**:
   - OS差異（Windowsのパス区切り文字 `\` とWebの `/`）やマルチプラットフォーム対応をバックエンドで一元吸収できる。
