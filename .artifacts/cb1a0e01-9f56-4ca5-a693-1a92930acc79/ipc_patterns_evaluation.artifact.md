# Tauri IPC パターン評価 (Brownfield Pattern vs Isolation Pattern)

Tauri 公式ドキュメントの `Core Concepts > Inter-Process Communication` に記載されている 2 つの主要な IPC 設計パターン（Brownfield Pattern と Isolation Pattern）の、本プロジェクト（`nanai-android-mascot`）における適合性評価。

---

## 1. Brownfield Pattern (ブラウンフィールドパターン)

### 概要
- WebView と Rust バックエンドの間で、標準の `invoke` / `emit` や `window.__TAURI_INTERNALS__.invoke` を介して直接通信を行うモデル。
- 現行の Nanai のメインウィンドウ、バルーン、およびコンテキストメニュー（`menu-iframe.html`）が採用している構成。

### メリット
- 実装がシンプルでオーバーヘッドが最小。
- 開発スピードが高く、多窓（メイン＋メニューiframe等）間のメッセージ中継が容易。

### デメリット / リスク
- サードパーティ製のゴースト（ネットからダウンロードした `.nar` 内の HTML / JS やカスタムスクリプト）を実行する場合、WebView 内から直接強力な Tauri IPC コマンド（ファイル削除、システムコマンド等）へアクセスできてしまうセキュリティリスクがある。

---

## 2. Isolation Pattern (アイソレーションパターン)

### 概要
- WebView と Rust コアの間に、専用のアイソレーションスクリプト（または中継レイヤー）を挟み、すべての IPC リクエストを一度インターセプト・無害化・検証してからバックエンドへ転送するモデル。

### メリット
- サードパーティ製ゴーストや未知のスクリプトによる不正な IPC コマンド呼び出し（XSS や権限昇格攻撃）を完全に遮断・制限できる。
- モバイル（Android）およびデスクトップ環境で、ローカルアセット実行の安全性を担保。

### 本プロジェクト（Nanai）における適用方針
- **サードパーティ製ゴーストの安全なサンドボックス化**: ゴーストが持つ独自HTMLやスクリプトが万が一不正な IPC を試みても、アイソレーション層（またはウィンドウスコープ / ケーパビリティ制限）でガードする。
- メニュー iframe やバルーン内の通信においても、信頼されたオリジンからのメッセージのみを許可する検証レイヤーを強化する。
