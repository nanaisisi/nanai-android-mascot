# システムトレイ初期化トラブルシューティングとアーキテクチャ知見

本ドキュメントは、Tauri v2 アプリケーション（`nanai-android-mascot`）におけるシステムトレイ（`TrayIcon`）の実装・トラブルシューティングの過程で得られた重要な設計知見の記録です。

---

## 1. 発生した問題と根本原因

### 問題1: タスクトレイにアイコンが表示されない

Windows環境等でアプリケーションを起動した際、システムトレイ（タスクトレイ）にアイコンが全く表示されず、セットアップ処理のログやエラーも一切出力されなかった。

#### 根本原因

1. **ビルダーの `.setup()` の二重定義（上書き）**:
   - Tauri の `tauri::Builder` では、複数の `.setup()` メソッドをチェーニングすると、**後から呼ばれた `.setup()` が前のものを上書き（破棄）してしまう**仕様がある。
   - 本プロジェクトの `src-tauri/src/lib.rs` の後半（`run()` 関数の末尾付近）に、過去の残骸である空の `.setup(|_app| { Ok(()) })` が存在しており、前半で記述したシステムトレイ登録（`tray::setup_tray(app)`）を含む setup ブロックが完全に無効化されていた。
   - **歴史的経緯**: 2026年10月31日のコミット（`d223ab41`：「Compatibility rs」）において、FMO関連のミューテックス獲得処理を追加する際に末尾へ追加された `.setup()` が、その後のリファクタリングで空のまま残り、プライマリの setup を覆い隠していた。
2. **所有権の即座の破棄（Drop）**:
   - `setup_tray` で生成した `TrayIcon` インスタンスをローカル変数（`let _tray = ...`）として受け取っていたため、スコープを抜けた瞬間にインスタンスが破棄され、OSのタスクトレイからアイコンが即座に消滅していた。

---

### 問題2: トレイメニューの出現位置が画面右上へ跳ね上がる

トレイアイコンをクリックした際、コンテキストメニューがタスクバー（右下）付近ではなく、画面の右上（`y = 0`）に表示されていた。

#### 根本原因

1. **境界判定時の2重高さ引き算バグ**:
   - `show_menu_window` 側で「画面下端からはみ出ない限界座標 (`max_y = 画面高さ - メニュー高さ720px`)」を超過した場合に、さらにメニュー高さ（720px）を引き算する上方向展開ロジックが走っていた。
   - これにより `y` 座標がマイナスになり、最後の画面内クランプ処理（`.max(0)`）で画面最上部（`0`）に張り付いてしまっていた。
   - **歴史的経緯**: 2026年10月28日のコミット（`51605e00`）でサブメニュー上方向展開用に導入されたロジックであったが、その後の全29項目メニュー拡張（高さ720px化）に伴い、トレイ座標との組み合わせで本計算バグが発生した。

---

## 2. 解決策・実装上のベストプラクティス

1. **`.setup()` は必ず単一のブロックに集約する**:
   - Tauri ビルダーの `.setup()` は複数チェーンせず、1つのブロック内にすべての初期化処理（トレイ登録、ウィンドウ先行キャッシュ等）を集約する。
2. **Tauri アプリ状態（State）への管理登録**:
   - 生成した `TrayIcon` は `app.manage(tray)` および `AppState.tray_icon` に保持し、アプリケーションのライフサイクル全体を通じて所有権を維持する。
3. **ネイティブアイコン形式の採用**:
   - Windows環境では、公式の Windows ネイティブアイコン形式（`.ico`）または Tauri 標準の `app.default_window_icon()` を使用する。
4. **トレイポップアップ位置の直接指定とシンプルなクランプ**:
   - トレイアイコンからのポップアップ位置は `(screen_width - win_width - offset, screen_height - win_height - offset)` で画面右下を直接指定し、メニュー側では単純な境界クランプ（`target_y.min(max_y).max(screen_pos.y)`）にとどめる。
