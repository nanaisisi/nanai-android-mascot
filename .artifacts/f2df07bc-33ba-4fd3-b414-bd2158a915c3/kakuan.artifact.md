# 各案：アーキテクチャ案の比較と多面的な検討（API・メモリ・改変性）

## 2.1 アーキテクチャの3つのアプローチ（各案）

| 比較項目 | 案1: フルRustフロントエンド化 (Yew / Dioxus) | 案2: ハイブリッド WASM/Rust コア + TS UI (推奨) | 案3: 段階的ホットスポットオフロード |
| :--- | :--- | :--- | :--- |
| **概要** | UIコンポーネントも含めてすべて Rust (WASM) で構築 | コアロジックを WASM に集約し、UI/DOM操作はTSのまま | 既存TSコードを維持し、重い処理だけを個別にWASM化 |
| **パフォーマンス** | 極めて高い | **極めて高い（計算はRust、描画はDOM）** | 部分的 |
| **開発コスト** | 非常に高い（既存UI/CSS資産の全面再構築） | **中程度（明確なIPC/WASM境界の定義）** | 低い（ただし技術負債が残る） |
| **Web API利用** | Rust側のWebフレームワーク経由 | **`web-sys` / `js-sys` で直接かつ自由に呼び出し可能** | 限定的 |
| **推奨度** | 低（リスク・コスト超過） | **最高（実用性とパフォーマンスの最適解）** | 中（移行の過渡期向け） |

## 2.2 多面的な評価・検討軸

### ① API利用の容易さと柔軟性
- **WASMの優位性**:
  - `web-sys` クレートを使用することで、Rust コードから直接ブラウザ標準の Canvas 2D 描画コンテキスト、`requestAnimationFrame`、`AudioContext`、`fetch`、DOM操作などを呼び出すことができます。
  - Tauri の IPC（`invoke`）と Web API を Rust という単一の言語コンテキスト内でシームレスにブリッジできるため、API呼び出しの複雑さが大幅に軽減されます。

### ② メモリ管理とゼロコピー（Zero-Copy）の実現
- **バッファ共有**:
  - 画像ピクセルデータ（RGBA）やサーフィスフレームバッファは、WASM のメモリ空間（`WebAssembly.Memory`）を TypeScript 側から `Uint32Array` / `Uint8ClampedArray` のビューとして直接共有します。これにより、JSとWASM間のデータコピーコストがゼロになります。
- **ライフサイクルとGC対策**:
  - Rust 側で確保したヒープメモリは、明示的な `destroy()` や `WeakMap` による参照管理を行い、メモリリークや意図しないメモリ肥大化を確実に防止します。

### ③ 改変性・拡張性 (Modifiability)
- **モジュール分割**:
  - パーサー、アニメーションエンジン、ピクセル合成などのドメインロジックが Rust のクレートとして完全に独立するため、単体テスト（`cargo test`）や機能改変が非常に安全に行えます。
- **プラグインエコシステム**:
  - 将来的に外部シェルの追加やカスタムSHIORI拡張をロードする際、サンドボックス化された WASM バイナリとして安全にプラグイン化できる高い拡張性を備えています。
