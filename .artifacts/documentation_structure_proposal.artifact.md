# ドキュメント3層構造の定義と整理方針（提案）

現在の `docs/` 配下において、仕様書が `doc//` や各ドメインフォルダに重複・散在している「雑多」な状態を解消し、見通しの良い管理を行うための構造定義と整理方針です。

ご提示いただいた **「内部文書（雑多） → 外部リポジトリ（整理・細分化） → 突合文書」** という情報の流れをベースに、以下の3層構造にドキュメントを整理することを提案します。

## 🏛️ ドキュメントの3層構造（アーキテクチャ）

### 第1層：内部文書（Nanai Android Mascot 独自の実装方針・設計）

- **格納場所**: `docs/doc/` 以下の各ドメインフォルダ (`developer/`, `design/`, `platform/`, `ghost/`, `shiori-script/` 等)
- **役割**:
  - 本プロジェクト固有のアーキテクチャ、設計思想、WASM・Tauri等を用いた独自の実装方針をまとめる。
  - 「伺かの仕様」を解説するのではなく、「その仕様をどうやってAndroidアプリとして実現するか」に特化する。
- **今後の整理タスク**:
  - 現在 `doc/nam-spec/` にすべての仕様書が集約されている一方、`doc/ghost/` や `doc/shiori-script/` 等にも同名ファイルが存在し重複しています。
  - これらをドメイン（機能別）ごとに1つのファイルへ統合し、「雑多」な状態を解消します。

### 第2層：外部リポジトリ（公式・標準プロトコル仕様）

- **格納場所**: `docs/ukadoc-spec/` , `docs/ukadoc-ssp/` (Git サブモジュール)
- **役割**:
  - 伺か（SHIORI, さくらスクリプト, プラグイン等）およびSSP拡張仕様の**公式ドキュメント（正本）**。
  - 整理・細分化された客観的なリファレンスとして機能する。
- **今後の整理タスク**:
  - 外部のドキュメントリポジトリであるため、原則として直接的な編集は行わず、最新状態を pull して参照し続ける情報源とします。

### 第3層：突合文書（実装適合・カバレッジ管理）

- **格納場所**: `docs/spec/` (主に `SUMMARY.md` およびサブディレクトリ)
- **役割**:
  - 「第2層の公式仕様」と「第1層の実装設計」を突き合わせ（突合）、**現在の実装適合度（✅ 実装済 / ⚠️ 一部対応 / ❌ 未実装）をトラッキング**する。
  - 開発の進捗管理（次期フェーズのTODOリスト）としての役割も担う。
- **今後の整理タスク**:
  - 内部文書に散らばっている互換性のメモや適合ステータスを、この突合文書（`docs/spec/`）へ集約し、自動集計マスタ（`SUMMARY.md`）と連携させます。
