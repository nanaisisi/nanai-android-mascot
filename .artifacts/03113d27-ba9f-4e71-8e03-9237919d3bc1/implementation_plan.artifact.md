# 総合メモリ最適化計画 (目標: 600MB -> 90MB水準)

SSP (PC環境) の約90MBに対して、現在のAndroidリリースビルドで約600MBに達している原因を特定し、最適化を行うための新規計画です。Tauri (Rust + WebView) アーキテクチャ特有のオーバーヘッドと、画像リソースのメモリ管理が主な原因と推測されます。

## 課題の仮説と分析方針

現在のメモリ（600MB）がどこで消費されているかを明確にする必要があります。考えられる主な要因は以下の4点です。

1. **WebView (フロントエンド) のオーバーヘッドと画像保持**
   - WebView自体が100MB前後を消費します。
   - DOM上に展開された画像（サーフェス、バルーンなど）やCanvasのメモリ領域が解放されずに蓄積している可能性。
2. **Rust (バックエンド) 側のオンメモリ画像キャッシュ**
   - `nanai-surface` などのコアエンジンで、サーフェス画像や差分パーツのRGBAピクセルデータを無制限（あるいは上限高め）にメモリにキャッシュしている可能性。
3. **データ転送 (Rust -> WebView) におけるメモリの二重持ち**
   - 画像データをBase64エンコードなどで送っている場合、Rust側とJS側の両方でデータを保持し、さらに文字列化のオーバーヘッドでメモリを圧迫します。
4. **Shiori (ゴーストスクリプト) エンジンのメモリリーク・保持**
   - JNI/WASM/FFI経由で動作するShiori（YAYA, Kawariなど）側のメモリ消費。

## フェーズごとのアクションプラン

### フェーズ 1: 計測とボトルネックの特定 (プロファイリング)
何よりもまず「何がメモリを食っているか」を可視化します。
- **Android Studio Profiler (Memory)**: 端末を接続し、Memory Profilerで「Java Heap (WebView等)」「Native Heap (Rust)」「Graphics (GPU/テクスチャ)」の割合を確認します。
- **WebViewのリモートデバッグ**: `chrome://inspect` でAndroid上のWebViewに接続し、MemoryタブでJSヒープとDOMノード/Canvasのサイズをスナップショットで確認します。
- **Rust側のヒーププロファイリング**: 必要に応じてRust側の割り当て(alloc)アロケータを監視します。

### フェーズ 2: Rust側の画像管理と合成処理の最適化
- **Surface合成時のバッファ削減**: `nanai-core/src/surface_compositor.rs` 等での重ね合わせ処理時、無駄な中間バッファを削減します。
- **キャッシュ戦略の導入**: 現在キャッシュしているデコード済み画像に対して、厳密なLRU（Least Recently Used）キャッシュや、メモリ上限（例: 20MB）を設定し、古い表情差分などを適時 `drop` します。

### フェーズ 3: フロントエンド(WebView)のレンダリング最適化
- **カスタムプロトコルの活用**: `tauri://` スキームを用いたストリーミング転送を徹底し、Base64等によるメモリの無駄を省きます。
- **DOM / Canvasからの適時破棄**: 表示されなくなったキャラクターのSurfaceやBalloonのDOM要素（またはテクスチャ）を確実に破棄（ガベージコレクションの対象）する仕組みをUI側（`ui/` の TypeScript）に実装します。

### フェーズ 4: バックグラウンド時のリソース解放
- **Androidライフサイクルとの連携**: アプリがバックグラウンドに回った際(`onTrimMemory` 等の検知時)に、WebViewの休止状態化や、Rust側の画像キャッシュを全クリアする仕組みを導入し、OSからキルされるのを防ぎます。
