## 2. 実行環境方針: WebView 主導 + 軽量 Rust バックエンドモデル

画面表示およびユーザーインターフェース (UI) の実行環境として **Tauri v2 の WebView（HTML5 Canvas 2D / CSS3 / TypeScript）** を軸とした最適化ハイブリッドモデルを採用します。

### メモリ膨張（Windows 800MB問題）への対策と役割分担

```
[ フロントエンド: WebView (Chromium V8) ]
  ├── UI レンダリング (Canvas 2D / CSS3)
  ├── アセット表示・V8 ネイティブグラフィックス
  ├── 必要に応じた V8 標準 WebAssembly (WebAssembly.instantiate) 実行
  └── ユーザー入力イベントのキャプチャ (Click / Drag)
         │ (Tauri IPC Bridge / 二重保持の排除)
[ バックエンド: Rust / Native (NDK) ]
  ├── SHIORI 3.0 コアエンジン制御 (里々 / YAYA / 華和梨)
  ├── 仮想ファイルシステム (VFS) & ストリーミング解凍
  ├── メモリ最適化 & 画像キャッシュクリア (`onTrimMemory`)
  └── OS 透過 / ウィンドウタッチスルー制御 (`WindowManager`)
```

- **二重持ちの排除**: 画像データや大規模バッファを Rust ヒープと JavaScript (V8) ヒープで二重保持する設計を見直し、WebView2 側の V8 エンジン能力をフル活用することで Windows 版でのメモリ膨大化（800MB 超）を抑制。
- **二重ランタイムの排除**: Rust 側で重い WASM インタープリタを動かさず、WASM が必要な場合は V8 の高速 JIT 付き WASM ランタイムに委ねる。

## 3. WASM ランタイム (`wasmi`) 削除による最適化

### 削る理由と得られる効果
- **結論**: **通常ビルドにおいて `wasmi` 依存関係および `nanai-shiori-vm` の `wasmi` 実行パスは削除・オプショナル化する。**
- **削減効果**:
  1. **バイナリサイズ（APK容量）の削減**: WASM デコーダ・検証器・中間表現エンジンが削られるため、リリースビルドで **数 MB（約 2MB〜5MB 以上）** の軽量化を達成。
  2. **ヒープメモリの節約**: `wasmi` の `Engine`/`Store` インスタンスおよび WASM リニアメモリ（Linear Memory）領域の占有がなくなるため、Android の Low Memory Killer (LMK) 対策に直結。
  3. **ライセンス表記の簡素化**: `wasmi` 関連依存クレートが引き込む大量のサードパーティライセンス文章を削除し管理コストを低減。

## 4. 動的ライブラリ (`.so` / `.dll`) の読込・配信戦略

Android 10+ (API 29+) の W^X ポリシーおよび Google Play 規約（DCL 禁止規定）を踏まえ、配信ルートとリンク手法に応じた詳細な分類を規定します。

### 4.1 同梱型エンジンにおけるトレードオフ評価と当面の方針

主要 SHIORI エンジン（里々・YAYA・華和梨）の組み込みにおいて、ビルド・リンク手法による特性を評価し、**当面は「静的同梱（Static Linking）」を最優先採用** します。

#### トレードオフ構造
- **ファイルサイズ (APK容量)**: **「直接的な増大」**（C++ コードが直組み込みされるため物理的に数MB増える）。
- **メモリ消費 (RAM使用量)**: **「間接的な関係」**（OS の Demand Paging が機能するため、使用されないコード自体が直接 RAM を圧迫するわけではない。動的なヒープ割り当てのみが影響する）。

| リンク手法 | ビルド構造 | 特徴・評価 | 当面の方針 |
| :--- | :--- | :--- | :--- |
| **① 静的同梱**<br>(Static Link / `build.rs` + `cc`) | C++ ソースを `.a` または Rust バイナリ本体に直接マージ | ・`dlopen()` 不要で **100% 確実に動作**<br>・LTO (Link Time Optimization) が機能し最速<br>・ファイルサイズは直接増えるがメモリへの影響は間接的 | **採用 (標準方針)**<br>動作の確実性・最高速・シンプルな実装を優先し、主要エンジンは静的同梱で構築。 |
| **② 同梱 `.so` 動的ロード**<br>(Bundled `.so` + `dlopen`) | 個別の `.so` として APK 内 `lib/arm64-v8a/` に格納し実行時 `dlopen` | ・不要なエンジンのメモリを `dlclose()` で完全解放可能<br>・ファイルサイズの増大を個別に制御可能 | **将来のメモリ最適化オプション**<br>将来的にエンジン数が非常に増えた場合のメモリ節約オプションとして保持。 |

### 4.2 配信ルート別の動的ライブラリロード設計

| 配信ルート | 手法 | 動的ロード可否 | セキュリティ / 規約 | 運用・特徴 |
| :--- | :--- | :---: | :---: | :--- |
| **① 事前同梱型**<br>(全環境共通) | NDK コンパイル済（静的同梱 or 同梱 `.so`） | ⭕️ **可能** | ⭕️ **完全適合** | 定番 SHIORI（里々・YAYA・華和梨）は APK 内に直接ビルド・同梱（最高速・オフライン完全対応）。 |
| **② 半同梱型**<br>(Google Play 版) | **Dynamic Feature Modules (DFM)** / Split APK | ⭕️ **可能** | ⭕️ **公式承認** | Google Play 公式のオンデマンド機能。OS の `dlopen()` 許可パスに配置されるため規約クリアして後入れ可能。 |
| **③ サイド配信型**<br>(GitHub / 野良 APK) | **自前サーバー / SD カードからの動的ロード** | ⭕️ **可能**<br>(サイド配信) | ⭕️ **規約枠外** | Google Play の DCL 規約が適用されない自由配布版。サードパーティ製 `.so` や拡張プラグインをユーザーの責任で自由にロード可能。 |

## 5. 実証・検証アプローチ: Windows-First 段階展開

各手法（WASM、静的同梱、DLL/動的ロード）の実装検証およびデバッグを高速化するため、**「Windows 環境での先行実証」** を開発プロセスとして定義します。

### 各方式の Windows での実証プロセス

1. **WASM (WebView V8) の実証**:
   - WebView2 (Edge Chromium) の DevTools および JavaScript (`WebAssembly.instantiate`) を使用し、`.wasm` モジュールの即時ロード・V8 上での実行性能・JS 連携をその場で高速検証。
2. **静的同梱 (Static Linking) の実証**:
   - `build.rs` + `cc` クレートにより、Windows 上で C++ ソース（里々/YAYA/華和梨）を `.lib` としてコンパイルし、Rust から直接 C-ABI 関数を呼び出す構成を検証。
3. **DLL / 動的ロードの検証**:
   - Win32 / 64bit DLL を `libloading` で動的ロードし、既存ゴーストとの互換性およびライフサイクル動作を直接デバッグ。

上記により Windows 上で高速にロジックを確立・安定させた後、Android NDK / System WebView 環境へ安全に展開・適用します。

## 6. Nanai の最終アーキテクチャ・ロードマップ

1. **フェーズ 1 (ベースライン & 軽量化)**:
   `wasmi` 依存関係を整理してビルドサイズを数 MB 削減。定番エンジン（里々・YAYA・華和梨）の C++ ソースを Windows 上で実証の上、Android NDK (ARM64 + Bionic) 用に **静的同梱 (Static Linking)** してコンパイル（確実性・最高速を優先）。
2. **フェーズ 2 (ストア版半同梱型 DFM)**:
   Google Play 配布版において、将来の大型エンジンや追加アセットを Dynamic Feature Modules (DFM) で分割し、必要時にオンデマンド取得。
3. **フェーズ 3 (サイドローディング & 即時 Web 拡張)**:
   GitHub / 野良配信版では「サイド配信型」として追加 `.so` の自由ロードを解放。また即時バグ修正が必要な場合は WebView (V8) 内での WASM 動的取得・実行を活用。
