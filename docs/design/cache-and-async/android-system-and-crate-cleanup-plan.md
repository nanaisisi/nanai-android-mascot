# Android OSシステム連携とRustクレート整理の検討実行計画

本ドキュメントは、Android OS標準機能の活用（キャッシュ・ライフサイクル・ストレージ）と、Rustクレートのスリム化・責務分離を段階的に推進するための検討事項および実行手順をまとめます。

---

## 1. 検討方針：責務境界の整理

Android OSがネイティブで提供する仕組みとRustの責務を以下のように切り分けます。

| 領域 | Android OS / Tauriプラットフォームの責務 | Rust側の責務 | 狙い・効果 |
| :--- | :--- | :--- | :--- |
| **キャッシュストレージ** | `context.cacheDir`（内部キャッシュ）の領域提供とOS自動パージ管理 | キャッシュディレクトリ配下のファイルI/O、インデックス管理 | OSの容量管理・ユーザーによる「キャッシュ削除」と完全同期 |
| **メモリ監視・解放** | `ComponentCallbacks2.onTrimMemory()` の監視と通知 | L1インメモリLRUキャッシュの段階的破棄（`TRIM_MEMORY_RUNNING_CRITICAL`等） | OOM Killerによる強制終了を防止 |
| **ロケール・言語** | Android `Configuration` / WebView `navigator.language` | ロケール文字列を受け取り翻訳辞書を切り替えるのみ | `sys-locale` などの外部クレート削減 |
| **静的初期化** | プラットフォーム初期化ライフサイクル | `std::sync::LazyLock` / `std::sync::OnceLock` | `once_cell` クレートの完全廃止 |
| **テキスト解析** | なし | 高速スライス走査（`std::str`） | `regex` クレートへの依存を極力排除しバイナリ削減 |

---

## 2. クレート整理の実行計画

### 2.1 即時実行（依存クレートのスリム化）

- **`once_cell` の廃止**:
  - Rust 2024 / 1.70+ の標準ライブラリ（`std::sync::LazyLock`, `std::sync::OnceLock`）へ置換。
- **`sys-locale` の検討・整理**:
  - フロントエンド（Tauri / JS）からロケールを渡す構造への切り替え、またはTauriの標準APIへ統合。
- **`regex` の利用箇所精査**:
  - パス走査やプロトコルヘッダパースで過度な正規表現を使用していないか確認し、標準文字列操作へリファクタリング。

### 2.2 ワークスペース構成の再編（検討・分割）

将来的にWASMビルドやAndroid ARMビルドで不要な依存を巻き込まないよう、以下のようなパッケージ分割を推進します。

```text
Cargo.toml (workspace)
├── src-tauri/             # Tauriアプリケーション本体・OSブリッジ
├── src/                   # フロントエンド資産 / Web-UI
└── crates/
    ├── shiori-core/       # SHIORI FFI / C++ 連携（OS非依存）
    └── ghost-archive/     # NAR / ZIP 展開・ファイルキャッシュ管理
```

## 3. Android OS連携の実行計画

### 3.1 キャッシュディレクトリの委譲

1. Tauriの `app.path().app_cache_dir()` またはJNI経由でAndroidの `context.getCacheDir()` を取得。
2. 合成済みサーフェスキャッシュ（L2）の保存先を同パス配下に固定。

### 3.2 メモリ圧迫通知（TrimMemory）のイベントハンドリング

1. Android側の `onTrimMemory` イベントをTauriのイベントシステム（またはJNIコールバック）経由でRustコアへ送出。
2. Rustのメモリキャッシュマネージャーがレベルに応じてキャッシュをクリア。

## 4. 既存エコシステム積極活用とセキュリティ統制方針

車輪の再発明を避け、すでに実績と安定性のある既存エコシステム（Android OS機能・Tauriプラグイン・npm・Rust標準/クレート）を積極的に活用します。同時に、Android WebView環境特有の攻撃面やサプライチェーンリスクに対し、厳格なセキュリティ対策を講じます。

### 4.1 エコシステム活用の役割分担

- **Android OS / ネイティブ基盤**:
  - キャッシュライフサイクル（`context.cacheDir`）や省電力スケジューラ（`WorkManager`）、メモリ圧迫通知（`onTrimMemory`）など、OS標準の堅牢な基盤を最大限に利用。
- **フロントエンド / npm エコシステム**:
  - Tauri公式プラグイン（`@tauri-apps/api` 等）や検証済み開発ツール（Biome, Markuplint）の積極活用。
  - 複雑なタッチジェスチャーやアニメーション処理など、自前実装で不具合が生じやすい領域は、枯れた軽量ライブラリの選定・活用を許容。
- **Rust エコシステム**:
  - 実証済みの安全なシリアライズ（`serde`）、暗号・圧縮（`zip`）を継続活用しつつ、最新のRust標準ライブラリ（`LazyLock` 等）で不要なサードパーティクレートを整理。

### 4.2 徹底するセキュリティ対策基準

1. **WebViewとIPC通信の境界保護**:
   - Tauriの権限スコープ（Capability / Permissions）を最小権限の原則（Least Privilege）で厳格に設定。
   - Rust側IPCハンドラで受け取るパス文字列・コマンド引数の厳格なサニタイズ（ディレクトリトラバーサル防止、NAR解凍時のZip Slip対策）。
2. **npm / サプライチェーンリスクの抑制**:
   - `npm audit` / lockfileによる依存バージョンの固定（ピン留め）。
   - 外部ライブラリ導入時は「推移的依存の少なさ」「パーミッション不要性」「ESMツリーシェイキング対応」を審査。
3. **Android Scoped Storage / サンドボックス保護**:
   - 外部ストレージへの無秩序な直接書き込みを避け、アプリ専用サンドボックスおよびSAF（Storage Access Framework）を徹底利用。

## 5. 将来構想：外部拡張性（Plugin / Extension Architecture）

現フェーズでは実装スコープから外し「設計上の配慮・検討留保（保留）」としつつ、将来的に取り込み可能な拡張ポイントとして構想を記録します。

### 5.1 想定される拡張ポイント

1. **外部SHIORI・AI/LLMバックエンド接続（プラグイン化）**:
   - 従来のC++ SHIORI DLL/so だけでなく、ローカルLLM（ONNX / llama.cpp / WebLLM）や外部APIベースの知能エンジンをスロットイン形式で差し替え可能にする構想。
2. **Web / WASM プラグイン機構**:
   - サードパーティがゴーストの特殊演出やミニゲーム、追加ツール（SAORI/PLUGIN相当）をWASMコンテナやWebWorker経由でサンドボックス実行できる仕組み。
3. **Android Intent / ContentProvider 連携**:
   - 他のAndroidアプリ（ランチャーや通知連携、マスコット連携ウィジェット）からゴーストへメッセージを送出・制御できる公開API設計。

### 5.2 現時点でのスタンス（意図的放置・凍結）

- **過剰設計（Over-engineering）の回避**:
  - 最初から複雑な動的プラグインローダーを組むと、Android ARM上でのバイナリ肥大化、セキュリティ検証コスト、メンテナンス負荷が跳ね上がる。
- **コア安定化の優先**:
  - まずは「Android OSキャッシュ・メモリ管理との完全同期」「Rustクレートの軽量化・責務分離」「確実な描画とSHIORI実行」を固めることを最優先とし、外部拡張のインターフェースはトレイト（抽象境界）のレベルで将来差し替え可能な余地を残すに留める。
