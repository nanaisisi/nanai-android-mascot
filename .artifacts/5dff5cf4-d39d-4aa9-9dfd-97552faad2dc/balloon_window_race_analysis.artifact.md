# バルーンウィンドウ連続起動（スコープ 0, 2, 3, 1）における不具合・競合解析レポート

本レポートは、以下のように複数スコープのバルーンウィンドウが連続して非同期呼び出しされた際に発生する不具合・競合原因を解析したものです。

```text
💬 show_balloon_window called: scope_id=0
💬 show_balloon_window called: scope_id=2
💬 show_balloon_window called: scope_id=3
💬 show_balloon_window called: scope_id=1
```

---

## 1. 根本的な原因の解析

### ① 存在しないキャラクターウィンドウ（スコープ 2, 3）への依存とフォールバックの乖離
- 標準的な伺かゴーストは通常、スコープ `0`（Sakura / メイン）およびスコープ `1`（Kero / サブ）の2キャラクター構成です。
- スコープ `2` や `3` のような拡張スコープに対して `show_balloon_window` が呼び出された際、対応するキャラクターウィンドウ（`subchar_window_2`, `subchar_window_3`）が未生成・または存在しないケースが多くあります。
- その結果、位置計算ロジック（`get_pos()`）において `app_handle.get_webview_window(&char_label)` が `None` となり、以下のハードコードされたフォールバック位置に強制配置されます：
  ```rust
  (200.0 + (scope_id as f64 * 220.0), 100.0)
  ```
- これにより、スコープ 2 や 3 のバルーンが予期せぬ画面座標（画面中央付近や重なった位置）に意図せずポップアップしてしまいます。

### ② WebView2 / Tauri UI スレッドの競合と並行生成負荷
- `0` → `2` → `3` → `1` という順序、かつ非同期かつ高頻度で複数の `show_balloon_window` が呼び出されると、Tauri の `WebviewWindowBuilder::new` がバックエンドの UI スレッド上でほぼ同時に複数ウィンドウの構築を試みます。
- Windows 環境（WebView2）では、短時間に複数の子ウィンドウを並行生成するとプロセス間の競合や初期化遅延、フォーカス泥棒が発生し、ウィンドウサイズや位置の適用不良を引き起こします。

### ③ 順序の逆転（`0 -> 2 -> 3 -> 1`）によるUIフローの混乱
- ゴーストの一般的な初期化・描画フローはメイン（0）からサブ（1）へと流れますが、途中にカスタムスコープ（2, 3）が割り込むことで、FMO（Mascot Object）の同期イベントやバルーン位置の自動調整（`sync_balloon_position`）のターゲットが定まらず、レイアウトの計算が錯乱します。

---

## 2. 改善・対策の提案

> [!IMPORTANT]
> 複数スコープのウィンドウ生成および位置同期を安定させるためには、以下の対策が有効です。

1. **ウィンドウ生成リクエストのキューイング / 直列化**:
   - `BALLOON_CREATION_LOCKS` による重複防止だけでなく、複数のウィンドウ生成要求を非同期キュー（Queue）で順次処理し、前のウィンドウの構築が完了してから次へ進むように制御します。
2. **存在しないスコープの検証**:
   - スコープ `2` 以上で対応するキャラクターが存在しない場合は、ウィンドウ生成をスキップするか、メインキャラクター（スコープ 0）の周辺に安全にフォールバックさせます。
3. **初期化順序の保証**:
   - ゴースト起動時のウェーブでは必ず `0` → `1` → 拡張スコープの順序でウィンドウを初期化・表示するようフローを保証します。
